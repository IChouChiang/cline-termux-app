# Architecture decision

_Generated on 2026-10-03 from `docs/research/kernel-and-desktop-synthesis.json` (multi-agent code reading of the Cline monorepo at cli-v3.0.68 + the Termux port). Line references point into `~/workspace/cline-termux-v3-phone`._

**Decision: `hybrid`** — a native Hub client for everything the Hub serves,
plus a thin Termux-side bridge over the `RUN_COMMAND` intent for lifecycle and the
surfaces the Hub does not expose.

## Rationale

Decision (final, per the owner's 'decide it now'): the app is a native Hub client for everything the Hub serves, plus a thin Termux-side bridge over the RUN_COMMAND intent for lifecycle and for the handful of surfaces the Hub does not expose. In the feature matrix, available_via=hub means the Hub WebSocket (ws://127.0.0.1:25463/hub, frames {kind:command|reply|stream.subscribe|stream.unsubscribe|event} per sdk/packages/shared/src/hub.ts:975-990); available_via=sidecar means the Termux-side bridge: a background RUN_COMMAND running the installed $PREFIX/bin/cline (`cline auth`, `cline config --json`, `cline history --json`, `cline hub start|status|stop|upgrade`, `cline doctor --json`) or the `cline dashboard` server's /browser WebSocket (apps/cline-hub, already in the Termux tarball: release/build-termux-release.sh:174,202 stages dist/cline-hub and @cline/cline-hub is bundled into index.js by apps/cli/bun.mts packages:'bundle'); available_via=files means a RUN_COMMAND `cat`/write of a ~/.cline file; none means no kernel path (Android-native or omitted). Why the Hub is the primary channel (all verified in code, not from the dossier alone): (1) the chat loop is complete over the Hub: session.create, run.start/session.send_input (server timeout null), run.abort, assistant.delta/reasoning.delta/tool.started|updated|finished/usage.updated/session.notice/run.completed|failed|aborted, durable replay via stream.subscribe.sinceSequence, pending prompts (queue/steer), session.list/get/messages/search/update/delete/restore/update_connection, settings.list/toggle, schedule.*, task.*, connector.*, ui.notify (hub-server-transport.ts:794-923). (2) Approvals need no ownership: handleSessionCreate wires requestToolApprovalHandler for every session (hub-server-transport.ts:814-826), approval.requested is published to the session's subscribers and re-issued on every subscribe, and handleApprovalRespond accepts any registered client (approval-handlers.ts; the dossier's 'creator only' claim is wrong — only capability.* requests are target-bound). (3) The daemon does the heavy lifting itself when the client contributes nothing: tools readFile/search/bash/webFetch/applyPatch/editor run in the daemon (extensions/tools/executors/index.ts:97-109; Android bash = $PREFIX/bin/bash, shared/src/parse/shell.ts:14), checkpoints are created daemon-side when sessionConfig.checkpoint.enabled=true (local-runtime-bootstrap.ts:546-556 createCheckpointHooks), auto-compaction is daemon-side (local-runtime-host.ts:683 createContextCompactionPrepareTurn), and rules/skills/workflows/plugins/hooks load daemon-side because DEFAULT_RUNTIME_CONFIG_EXTENSIONS is all five kinds when configExtensions is omitted and no userInstructionService is contributed (shared/src/session/runtime-config.ts:19,45-50; runtime-builder.ts:455-480). Only ask_question needs a client contribution (definitions.ts:971 requires executors.askQuestion) and the skills tool likewise (definitions.ts:964). (4) Upgrade auth is the Sec-WebSocket-Protocol entry `cline-hub-auth.<token>` or a loopback Origin header; no Authorization header is read on the upgrade (hub-websocket-server.ts:675-691) — OkHttp can send either. (5) Every first-party front end (CLI TUI, desktop sidecar, dashboard) is itself a Hub client, so the Hub protocol is the surface upstream must keep stable; coupling the app to it is the lowest maintenance burden against upstream churn. Why a bridge is still required: the Hub has no provider/model catalog, credential CRUD, OAuth sign-in, account, MCP CRUD, marketplace, file search or workspace browsing (catalog.list, cline.account.get_current, prompt_commands.*, mention_files.search, session.fork are declared but never dispatched; settings.get/patch answer not_implemented — hub-server-transport.ts:783-932), it cannot start itself, and its token lives only in Termux-private ~/.cline/data/locks/hub/production.json (0600; `cline hub status` never prints it). Those needs are met by (a) RUN_COMMAND `cline auth --provider X --apikey K --modelid M` (non-interactive, writes providers.json, sets lastUsedProvider), `cline auth cline` (WorkOS device flow, browser via xdg-open/termux-open), `cline config <target> --json`, `cline history --json|export`, `cline hub *`, `termux-wake-lock`; and (b) the shipped `cline dashboard --no-open` server for the richer settings surfaces (desktopCommand list verified in apps/cline-hub/src/server/desktop-commands.ts: list_provider_catalog, list_provider_models, save_provider_settings, add_provider, run_provider_oauth_login, cline_account, get_global_settings, set_telemetry_opt_out, set_auto_update_enabled, list/start/stop_connector_channel, list_mcp_servers, set_mcp_server_disabled, upsert_mcp_server, delete_mcp_server, ensure_mcp_settings_file, open_mcp_settings_file, get_process_context, list_cli_sessions, list_discovered_sessions, search_sessions, read_session_hooks, list_user_instruction_configs, list_marketplace_installed_entries, install/uninstall_marketplace_entry, uninstall_local_primitive, toggle_disabled_plugin_tool, set_tool_disabled, set_plugin_disabled; plus loadModels/loadProviderCatalog/saveProviderSettings/runProviderOAuthLogin messages). The dashboard is started on demand (it is a second Bun process with its own ClineCore) and the design degrades to RUN_COMMAND-only if its Bun.serve WebSocket turns out not to work on bun-android-ffi (blocking unknown 3): providers = `cline auth`, models = a bundled static list per provider plus free-text model id, account = omitted. Tier 1 and the Tier 2 core (sessions/history/model switch) depend only on the Hub and RUN_COMMAND.

## Rejected alternatives

sidecar-in-termux (run apps/examples/desktop-app/sidecar inside Termux and speak its ws://127.0.0.1:3126/transport): rejected. It is not a runtime — it is itself a Hub client (ClineCore backendMode 'hub' + a 'code-sidecar-observer' NodeHubClient), so it adds a third ~300 MB-class Bun process on top of the Hub for no execution benefit; it hard-requires Bun.serve WebSockets on bun-android-ffi (unverified; the CLI port only exercises Bun as a ws client), an entry.js shim beside its own bundle, `ws` kept external, and a core build id identical to the CLI tarball's or the two will retire each other's Hub on every launch (compareHubBuilds in hub/discovery/index.ts); it silently auto-rejects every tool approval unless the client sends an allow-listed Origin plus the per-launch approval_token that is only printed on stdout (so the app would have to inject CLINE_SIDECAR_APPROVAL_TOKEN itself); it would need a new release artifact in the port; and its 113-command, unversioned protocol in apps/examples is coupled to the desktop webview and changes with every desktop release, with a third of it desktop-only (zenity/osascript folder picker, editor launch, Tauri updater/tray, remote SSH helpers, cloud sandboxes, Composio). The Hub protocol is versioned (v1) and durable; the sidecar's is neither. hub-direct only: rejected because it cannot bootstrap — no way to start the daemon, read the token, configure a provider or API key, sign in to Cline, list models, browse a workspace directory, or manage MCP/marketplace — and because upstream's design explicitly leaves credential and catalog management to in-process @cline/core helpers (local-provider-service.ts, ProviderSettingsManager) rather than the Hub. The Origin-header token-less upgrade path is not used as the default either: it is an upstream convenience for browser clients that may tighten, it grants only daemon-workspace authority (schedule/task scope), and the token is obtainable in one RUN_COMMAND. Also rejected: loading the `cline dashboard` webview in an Android WebView as the whole app (not Material 3, not the desktop feature set, and the owner asked for a native Compose app), and driving `cline --acp` over stdio (RUN_COMMAND stdin is one-shot and results arrive only on exit).
