# Kernel contract (Termux + Cline Hub)

_Generated on 2026-10-03 from `docs/research/kernel-and-desktop-synthesis.json` (multi-agent code reading of the Cline monorepo at cli-v3.0.68 + the Termux port). Line references point into `~/workspace/cline-termux-v3-phone`._

## Prerequisites On The Phone

Termux >= 0.109 (S25U has 0.118.x), allow-external-apps=true in ~/.termux/termux.properties (the owner confirmed it is already set), Cline Termux port >= v3.0.68-termux.2 (first build whose Hub daemon starts: entry.js + external ws; the current stable .1 cannot start it), optionally termux-setup-storage for workspace folders under ~/storage. Nothing else is installed in Termux by the app.

## App Manifest

android.permission.INTERNET; com.termux.permission.RUN_COMMAND (custom dangerous permission -> declare and request at runtime; the grant dialog is Termux's); <queries><package android:name="com.termux"/></queries> (API 30+ visibility); POST_NOTIFICATIONS (API 33+); FOREGROUND_SERVICE + FOREGROUND_SERVICE_SPECIAL_USE with <property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE" android:value="hub-session"/> (no timeout; sideloaded app), optionally FOREGROUND_SERVICE_DATA_SYNC as the Play-clean alternative with the 6 h/24 h budget; res/xml/network_security_config.xml with <domain-config cleartextTrafficPermitted="true"><domain>127.0.0.1</domain></domain-config> because ws:// to loopback is cleartext on API 28-36; an exported="false" BroadcastReceiver for RUN_COMMAND results.

RUN_COMMAND BRIDGE (one Kotlin class, every call typed): Intent action com.termux.RUN_COMMAND, component com.termux/com.termux.app.RunCommandService, started with startService() from a foreground state. Extras: com.termux.RUN_COMMAND_PATH = absolute executable (/data/data/com.termux/files/usr/bin/cline | cat | find | termux-wake-lock | termux-wake-unlock | pkill), com.termux.RUN_COMMAND_ARGUMENTS = String[] (no ~ expansion in arguments: use /data/data/com.termux/files/home/...), com.termux.RUN_COMMAND_WORKDIR = /data/data/com.termux/files/home, com.termux.RUN_COMMAND_BACKGROUND = true (APP_SHELL runner; no terminal session, no activity), com.termux.RUN_COMMAND_PENDING_INTENT = PendingIntent.getBroadcast(FLAG_MUTABLE or FLAG_ONE_SHOT) targeting the app's own receiver. Result Bundle extra "result": stdout, stderr, exitCode, err (-1 = none), errmsg; stdout+stderr truncated to 100 KB combined, so never use it for logs or transcripts. Results arrive only when the command exits; long-running commands (dashboard) are fire-and-poll. For the Cline OAuth sign-in where the browser cannot be opened from the background shell, use the foreground runner (BACKGROUND=false, SESSION_ACTION=0) so the user sees URL and code in Termux.

CONNECT SEQUENCE (every app start and every resume): 1) GET http://127.0.0.1:25463/health with a 1 s timeout; if ok, require protocolVersion "v1" and remember buildId/coreVersion; GET /version gives pid+startedAt. 2) If refused: RUN_COMMAND `cline hub start` (background; exits when the daemon is up, last stdout line = ws URL; 8-15 s cold on the S25U), then RUN_COMMAND `termux-wake-lock` (acquires Termux's PARTIAL_WAKE_LOCK + WifiLock and keeps TermuxService in foreground-service state, which is what keeps the Hub alive: the Hub is a detached child in Termux's process group and dies with it). 3) Token: if the cached token's (hubId, pid, startedAt) differ from /version, RUN_COMMAND `cat /data/data/com.termux/files/home/.cline/data/locks/hub/production.json` and parse {authToken (64 hex), hubId, pid, port, url, buildId, coreVersion}; store authToken in DataStore encrypted with an Android Keystore AES key (never log it; never write it to the repo). The token rotates on every daemon start. 4) OkHttp WebSocket to ws://127.0.0.1:25463/hub with request header Sec-WebSocket-Protocol: cline-hub-auth.<token>; on HTTP 401 re-read the token once; keep the no-token path (Origin: http://localhost, reduced authority) only as a diagnostic fallback behind a developer switch. 5) Send command {version:"v1", command:"client.register", requestId, clientId, payload:{clientId, clientType:"android", displayName:"Cline Termux", transport:"native", actorKind:"client", capabilities:[{name:"approval.respond"},{name:"tool_executor.askQuestion"}], metadata:{version, platform:"android", pid:0}, workspaceContext:{workspaceRoot:<last workspace>, cwd:<same>}, protocolVersion:"v1"}}; clientId is a stable per-install id ("android-<uuid>") reused across reconnects like NodeHubClient. 6) Frame {kind:"stream.subscribe", clientId, sinceSequence:<persisted global cursor>} and, for each open session, {kind:"stream.subscribe", clientId, sessionId, sinceSequence:<persisted per-session cursor>}; persist the highest sequence seen per key after every event; pending approvals are re-issued on each subscribe (dedupe by approvalId). 7) For an open session that is live: session.attach {sessionId}; for one that is not (daemon restarted): session.create {sessionConfig:{sessionId:<old>,...}, initialMessages:<session.messages result>}.

## Keep-Alive

the Hub pings every 30 s and terminates a socket that misses one sweep; OkHttp pongs automatically while the process is unfrozen. Android freezes a cached app ~10 s after it leaves the foreground and kills its TCP sockets, so: start the specialUse foreground service (notification "Cline is working...") when a turn starts or a session is attached with "keep connected" on, stop it when the run ends (run.completed|failed|aborted) and no approval/question is pending; otherwise accept the disconnect and resync on resume. All command replies must be optional: terminal truth is the event stream, and session.send_input is issued with timeoutMs:null and the request kept only as a correlation id. Reconnect policy copied from NodeHubClient: delay min(250 ms * 2^attempt, 5 s) with 50 % jitter, re-register with the same clientId, re-subscribe with cursors, re-attach sessions; pending commands fail with hub_connection_closed and are not retried except idempotent reads.

## Termux Liveness And The Hub'S Lifetime

the Hub has no idle exit (~300 MB RSS measured on the S25U) and dies when TermuxService stops and Termux is evicted (AOSP kills the whole process group). The app therefore: holds termux-wake-lock while "connected", offers "Stop kernel" (RUN_COMMAND `cline hub stop`, then `termux-wake-unlock`) and "Disconnect (keep Hub)" in Kernel settings, shows a "Termux asleep / Hub down" state when /health fails and offers "Start kernel", and shows the One UI checklist once (Termux and this app: Battery > Unrestricted; add both to Never sleeping apps; Developer options > Disable child process restrictions, verifiable with adb `settings get global settings_enable_monitor_phantom_procs`). Before shipping, the owner's pending decision in CLAUDE.local.md (is a Hub left running in the background acceptable?) becomes the default of the "keep Hub running after exit" switch.

ON-DEMAND SETTINGS HELPER (the shipped dashboard server): when the user opens Providers, Account, MCP or Marketplace: GET http://127.0.0.1:8787/health; if down, RUN_COMMAND background `cline dashboard --no-open --host 127.0.0.1 --port 8787` (the command does not exit; poll /health up to 20 s), then OkHttp WebSocket to ws://127.0.0.1:8787/browser with header Origin: http://127.0.0.1:8787 (both Host and Origin must be in the allow-list; no roomSecret on loopback); send {type:"ready"}, then {type:"desktopCommand", id, command, args} -> {type:"desktopCommandResult", id, ok, result|error}, {type:"loadModels", providerId} -> {type:"models"}, {type:"loadProviderCatalog"} -> {type:"provider_catalog"}, {type:"runProviderOAuthLogin", providerId} -> {type:"provider_oauth_login_done"}. The dashboard also ensures the Hub and registers as "cline-hub-chat"/"cline-hub-server" clients. Stop it when leaving settings: RUN_COMMAND `pkill -f "index.js dashboard"`. If blocking unknown 3 fails (Bun.serve on the device Bun), this helper is dropped and the same screens fall back to RUN_COMMAND `cline auth ...` plus bundled model lists.

## Recovery Matrix

upgrade 401 -> stale token -> re-read production.json; ECONNREFUSED on 25463 -> `cline hub start`; RUN_COMMAND result err != -1 with errmsg mentioning allow-external-apps or permission -> Kernel setup screen with the exact fix; Termux not resolvable via <queries> -> "Install Termux" screen; reply error hub_draining (retryable) -> wait for hub.drain_changed; session_not_found on send -> resume via session.create with sessionConfig.sessionId + initialMessages; run.interrupted {runId, error, reason:"hub_restart"} -> mark the run interrupted and offer resend (caveat: the Hub publishes it only from HubRunQueue.recoverOnStartup() for runs admitted via run.enqueue, hub-server-transport.ts:683-695; the app's own session.send_input = run.start turns never get it, so detect those from an open run.started with no terminal run.* plus a changed /version pid/startedAt on reconnect or the replayed shutdown projection (run.completed {reason:"disposed"}, or session.updated with snapshot.status cancelled/completed and endedAt) — design/screens/home-chat.md §1.3.4); approval.requested with no UI able to answer (app killed) -> re-issued on next subscribe, plus the notification deep-links to the session; capability.requested (ask_question) after reconnect -> cancelled by the Hub when the target client unregisters, so the turn continues without the answer; a RUN_COMMAND that never returns (hub start hung) -> 60 s timeout then `cline doctor --json` for diagnostics.

## Batch 1 Additions (Core 0.0.91, 2026-10-07)

Verified on the bench Hub (core 0.0.91) and the S25U; results in docs/10-batch1-report.md.

**Shared settings file.** The app reads `~/.cline/data/settings/global-settings.json` with `cat` and writes it only by a one-key merge run as `bun-ffi -e` through RUN_COMMAND (JSON on stdin, temp file plus rename, other keys untouched; `KernelGlobalSettingsCommands.write`). Keys it writes: `toolAutoApprove` (A1; a missing key means on, as in the terminal, `apps/cli/src/main.ts`), `compactionEnabled` and `compactionStrategy` (`agentic` = LLM, `basic` = Truncation; Off keeps the strategy, as `setCompactionModeGlobally` does). The terminal reads the same keys, so both clients share the setting.

**Tool policies on every create path.** `sessionConfig.toolPolicies` as the terminal builds them: Auto-approve all = `{"*":{autoApprove:true}}`; Ask each time = `{"*":{autoApprove:false}}` plus `autoApprove:true` for the seven read-only tools of `SAFE_AUTO_APPROVE_TOOL_NAMES`. A session's policy is fixed when its runtime is created; to change it the app restarts an idle session it drives (`session.detach`, then `session.create {sessionConfig.sessionId:<same>, initialMessages:<session.messages>}`), at the end of a run it started or just before its next send, never while another participant is attached. Two record quirks of core 0.0.91: every `session.update` carrying metadata (a pin) drops `metadata.autoApproveTools`, and a resume stamps the new policy only in memory, so the `session.updated` / `run.*` records at the run's end (and `session.get` afterwards) carry the creation-time value again. The app therefore trusts the policy of the runtime's latest create it saw over any later record (`SessionState.createdAutoApprove`).

**Compaction.** Every `session.create` (new, resume, restore, fork) carries `sessionConfig.compaction`: `{enabled:true}` when the global keys are absent (core's auto-compaction is opt-in; G1), `{enabled:false}` for Off, `{enabled:true,strategy:"agentic"|"basic"}` otherwise. `session.compaction.get {sessionId}` answers `{sessionId, state?}` only to the client that created the session, and `session.detach` ends that right; the app reads it before a detach and passes it back as top-level `initialCompactionState` on the following create (run-boundary restart, act-mode rebuild), like the terminal's `restartWithCurrentMessages` (the app sends the state as read, without re-projecting it). A compaction change does not restart an open idle session; it applies at that session's next create.

**Client contributions.** `runtimeOptions.clientContributions` on every create path: the `askQuestion` tool executor, `{kind:"mistakeLimit", capabilityName:"mistake_limit.decide"}` (G2) and, for a session whose `sessionConfig.mode` is `plan` only, the CLI's `switch_to_act_mode` tool (`kind:"tool"`, `lifecycle.completesRun`). Runtime tools are fixed at create from the mode: after a successful switch the run ends, the app rebuilds the session in act mode (detach plus create, as above) and sends the CLI's continuation prompt in act mode; in an act runtime the tool does not exist. `ClientContributions` answers every `capability.requested` aimed at this client once (dedupe by `requestId`), the mistake-limit decision in the CLI's shape (`{action:"continue", guidance}` or `{action:"stop", reason:"stopped after mistake_limit_reached prompt"}`), and any unknown capability with `ok:false`, so a run never waits on the phone for something it cannot do. With no hold hooks, core keeps calling the model while the mistake-limit question is open (about 60 extra model calls in 11 s on the bench). A capability request is cancelled by the Hub when its owner's socket drops; core treats a cancelled decision as stop.

**Hooks.** The Hub runs the user's hook files itself (global `~/.cline/hooks/<Event>.sh`, workspace `.cline/hooks/<Event>.sh`) for every session, the app's included: core's default config extensions include `hooks`. A hook gets the event JSON on stdin and may print `{"contextModification":"..."}` (added to the next model request as `<hook_context>`) or `{"cancel":true,"errorMessage":"..."}`. In core 0.0.91 a cancelling `PreToolUse` stops the whole run, not only the call (`run.aborted`, no tool event, no tool result), and its `errorMessage` reaches no client (no event, message or log; an upstream report candidate). Hooks spawn in the session's cwd, so a session whose folder does not exist on the Hub's host cannot run them (`posix_spawn` ENOENT; the tool goes ahead). The app registers no hook contribution and never sends `configExtensions`: that would run each hook twice and make every tool call wait for the phone (TODO A3). `UserPromptSubmit` does not fire on the Hub path.

**Heartbeat.** `run.heartbeat {requestId, elapsedMs, timeoutMs, timestamp}` arrives every 30 s (`HUB_RUN_HEARTBEAT_MS`) while a run is open. The app raises its stall notice ("The kernel has been running for 30 s without responding", Keep waiting / Restart kernel) on a live heartbeat when no other event of that session arrived since the previous heartbeat (or since the run start plus 2 s for the first one) and nothing waits on the user or a tool; any other session event clears it. Stop and the approval sheet's Stop give up after the protocol's 30 s command timeout (`HUB_DEFAULT_COMMAND_TIMEOUT_MS`) and offer Restart kernel.

**Drain across a replacement Hub.** A replacement Hub replays the old Hub's `hub.drain_changed` events from the shared durable log. The draining flag belongs to the connection: each new connection's `hub.status` replaces it, a `hub.drain_changed` at or below that status's `lastSequence` is ignored, and the kernel state is re-derived when the connection generation changes (G5).

**Steer.** Long-press Send while a run is active sends `session.send_input {delivery:"steer"}`; the Hub injects the text into the running turn (the next model request of the same run carries it, and the in-flight stream is cut short). No queue entry.

**Checkpoints.** Core 0.0.91 creates checkpoints daemon-side for a plain client (`metadata.checkpoint.history`, kinds `commit` / `stash`, one per run; fixture 07). A restored or forked session's inherited history is written with numeric `createdAt`, as core's `createRestoredCheckpointMetadata` writes it.

**Termux-side files the app now touches.** Prompt history `~/.cline/data/cache/user_input_history.jsonl` (the terminal's file: oldest first, one `{"prompt","ts"}` per line, at most 20; read with `cat`, appended with a `bun-ffi -e` rewrite after a direct send the Hub accepted, as the terminal does). Task worktrees: `git worktree add` into `~/.cline/worktrees/<5 hex>/<repo name>` on branch `cline/<id>` (bash scripts with paths only as positional arguments); removed with the session unless another listed session lives in it, mirroring the desktop's `removeTaskWorktree`.

**Not delivered by the Hub (core 0.0.91).** Recoverable agent errors are dropped by `session-event-projector.ts` (`projectAgentErrorEvent` returns early on `recoverable`), so no client receives recovery notices (A11.9's inline half waits on an upstream change). No Hub command compacts on demand (A14).

## Batch 2 Additions (Core 0.0.91, 2026-10-08)

Verified on the bench Hub and the S25U; results in docs/11-batch2-report.md.

**Fork is whole-session only.** The app's one fork (decided A16, A19) reads `session.get` and `session.messages` and sends `session.create {initialMessages:<all messages>}` with `metadata.fork {forkedFromSessionId, forkedAt, source, checkpoints}`. It never cuts the history and never writes `fork.beforeRunCount`. It is reached from the chat's three-dot menu and the drawer's row menu; message rows have no fork and a typed `/fork` is plain text to the model. The user row's Edit is a different function, the checkpoint flow, and it still carries the edited run as `beforeRunCount`, as the desktop's edit-fork does. The batch-1 move to another workspace (delete, then create under the same id) is gone with A11.8: the app has no path that deletes a session in order to recreate it.

**Stop at the mistake limit.** No Hub event says why a run stopped: `run.aborted` carries only `aborted`, whether the user answered `stop` to `mistake_limit.decide` or the app gave up after its 5-minute wait. When the Hub accepts the app's `stop`, the app adds its own notice row to the transcript ("Stopped after repeated mistakes", with the kernel's latest detail as "Latest: ...", or "Stopped: the question was not answered within 5 minutes"). The notices live only in the app's `sessions` DataStore (`sessions.stopNotices`, newest 200) and are dropped with the session; the terminal, the desktop and `cline history export` never see them. The model call already in flight when Stop was answered still lands after the stop, so the row waits for the run's end and takes its time (trial row 21). The headline names no count because the kernel's `consecutiveMistakes` is not one on a loop stop: the loop detector records its hard verdict with `forceAtLimit`, which sets the counter to the limit (6 by default) after 5 identical calls.

**Interrupted tool calls.** Core 0.0.91 leaves a `tool_use` without a result when a cancelling `PreToolUse` hook ends the run (U5). The desktop projects such a history call as in progress. The app projects a call with no result in a finished turn as "Interrupted: <command, file or tool>" with a warning glyph (decided A21); a call in a live run still shows Running. This is presentation only; nothing is sent to the Hub.

**Titles at the first prompt.** Core 0.0.91 persists a brand-new session only at its first prompt (`ensureSessionPersisted`) and titles it from that prompt, over a title given at `session.create`. When this app sends the first prompt to a session whose stored title was set at create, it renames the session back with `session.update` about 1 s after that run ends, once, and only if the record still holds exactly the prompt-derived title (`CreateTitleKeeper`). Forks are persisted at create and keep their title.

**The session list is authoritative.** The Hub sends no event when another client deletes a session. Every `session.list` reply decides which rows exist; the app's list cache keeps only rows a list confirmed, and replayed events at or before the sequence seen just before a list request cannot add back a session that list did not return.

**Default folder.** A session started without choosing a folder sends the Termux home (`/data/data/com.termux/files/home`) as `workspaceRoot` and `cwd` (decided A22) instead of the kernel's chat-workspace path, which the app never created. The app writes nothing there.

**Teams and skills switches.** Core 0.0.91's `settings.list` returns plugin tools only, never the built-ins, so whether `teams` or `skills` is switched off is read where the desktop reads it: `global-settings.json` `disabledTools`, by `cat` at the send that needs it. `/team <task>` with Teams off is refused before anything is sent; the checks run in the desktop's order (usage, disabled, mode).

**Full commands.** A `run_commands` result's `query` is the kernel's 200-character preview with a truncation note. The app prints each command from the tool call's input (`commands[i]`, normalised as the kernel normalises it) and uses the preview only when the input is missing or does not match it, never showing the note.
